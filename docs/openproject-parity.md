# OpenProject Functional Parity Matrix

Reviewed: 2026-08-27 against OpenProject 17.7.2 (released 2026-08-13)

This is the auditable definition of OpenProject functional parity for Team Spaces. The current OpenProject [pricing matrix][op-pricing] is the canonical feature list; its [user guide][op-user], [Enterprise guide][op-enterprise], and [system administration guide][op-admin] define the source behavior.

**Audit state: core functional parity is achieved.** The corrected audit first downgraded connector labels and normalized directory ingestion that lacked provider behavior. Those five rows were promoted only after authenticated protocol adapters, verified callbacks, direct LDAPS authentication/querying, scheduled reconciliation, UI paths, production infrastructure, and automated evidence were added. This is a source-and-test claim for the defined core scope, not a claim that an undeployed installation or third-party tenant has passed operator-specific acceptance.

## Definition and status rules

Functional parity means that Team Spaces satisfies the acceptance criteria below for all current Community features and functional Enterprise add-ons from Basic through Corporate. It includes user, administrator, API, export, authentication, and maintained-integration behavior. Team Spaces may implement an equivalent workflow instead of copying OpenProject's UI, data model, deployment topology, or code.

Parity excludes hosting, billing, installation assistance, training, support channels, response-time SLAs, and other commercial services. BIM, the beta native mobile app, and unsupported third-party integrations remain separately tagged and do not block the core parity claim.

Equivalent workflows need not copy OpenProject's implementation protocol. In particular, Team Spaces supports direct LDAPS or an operator Cognito LDAP bridge, and its XWiki integration uses externally held provider credentials plus signed reverse callbacks instead of OpenProject's specific two-way OAuth authorization-code plugin. The parity judgment is based on authenticated browse/create/link/search and permission outcomes. A deployment must still run live conformance checks against its own LDAP, GitHub, GitLab, Nextcloud/openDesk, Microsoft, and XWiki tenants.

Status is conservative:

- **Implemented**: every criterion in the row has an end-to-end UI/API/persistence path and proportionate automated evidence.
- **Partial**: a working slice exists, but at least one criterion or important behavior is absent.
- **Missing**: no functional Team Spaces path was found. A label, mock display, or fixture alone does not count.
- **Separate**: intentionally tracked outside the core parity claim.

The evidence anchors are the [product scope](product-scope.md), [OpenAPI contract](../openapi.yaml), [API router](../services/api/src/routes/router.js), [production DynamoDB adapter](../services/api/src/repositories/dynamo.js), [web components](../apps/web/src/components/ui.js), [API acceptance suite](../services/api/test/api.test.js), [contract tests](../packages/contracts/test/contracts.test.js), and [infrastructure tests](../infra/test/community-profile.test.js).
